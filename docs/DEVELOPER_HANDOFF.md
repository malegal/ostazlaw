# دليل تسليم المطور — موقع مكتب جاد الرب

## نطاق الجولة الحالية

تم تحسين الموقع بهدف رفع التحويل إلى الاستشارة، وتحسين الظهور المحلي في محركات البحث، وجعل المحتوى أوضح لأنظمة الإجابة والذكاء الاصطناعي. ركزت الجولة على الصفحة الرئيسية، صفحة `services` الفعلية (`/sectors`)، وصفحة التخصصات (`/specialties`)، مع تحديث التنقل وصفحة التواصل اللازمة لمسار التحويل.

## مسار الزائر

يبدأ الزائر من رسالة الهيرو والدعوة إلى الاستشارة المجانية، ثم يختار من الصفحة الرئيسية فئة قريبة من حالته: فرد، شركة أو مستثمر. ينتقل الرابط إلى `/sectors` مع `#business` أو `#investor` أو `#individual`. داخل صفحة الخدمات، تمرر روابط الموضوعات `audience` و`specialty` إلى `/contact`، حيث يفتح نموذج التواصل بالموضوع المسبق ويقل عدد الخطوات المطلوبة من العميل.

صفحة `/specialties` هي بوابة تجميع: يفتح الزائر بطاقة التخصص، يقرأ الخدمات والخطوات، ثم ينتقل إلى نموذج الاستشارة أو طلب المقابلة. رؤوس البطاقات تستخدم `aria-expanded` و`aria-controls` وتدعم Enter وSpace؛ يجب الحفاظ على هذه السمات عند أي إعادة تصميم للتفاعل.

## ما تم تغييره

- توحيد اسم رابط `/sectors` الظاهر في الهيدر والتذييل إلى «خدماتنا».
- تحديث عناوين ووصف Open Graph والبيانات المنظمة للصفحات الرئيسية والخدمات والتخصصات.
- إضافة أسوان ومصر إلى `areaServed` في البيانات المنظمة.
- إبراز العقارات والعقود والمنازعات المدنية وخدمات الشركات والمستثمرين كتموضع أساسي، مع الإبقاء على التخصصات الأخرى دون وعود بنتائج أو مدد.
- تحسين صياغة بطاقات التخصصات لتكون مباشرة ومهنية، وإزالة عبارات الضمان والمبالغة.
- تفعيل خط IBM Plex Sans Arabic من الملفات المحلية في `public/fonts` باستخدام `@font-face`.
- تحسين وضوح شارات التخصصات على الشاشات الصغيرة وإضافة حالة تركيز للوحة المفاتيح.

## قواعد التحرير المستقبلية

عند إضافة تخصص أو خدمة، يجب أن يتضمن السجل عنوانًا واضحًا، ووصفًا يشرح الخدمة بلغة العميل، وقائمة خدمات فعلية، وسببًا مهنيًا لا يتضمن ضمان النتيجة. تجنب عبارات مثل «نضمن»، «نغلق كل الثغرات»، «حل سريع» أو «نتيجة مؤكدة» ما لم توجد صياغة قانونية دقيقة ومبررة.

يجب أن يتطابق الاسم والوصف وموقع المكتب بين `pages/index.js` و`pages/sectors.js` و`pages/specialties.js`. إذا تغير نطاق الخدمات أو بيانات المكتب، راجع `title` و`description` و`canonical` وJSON-LD وOpen Graph في الصفحات الثلاث.

## التحقق المحلي

من مجلد المشروع:

```bash
npm ci
npm run build
git diff --check
```

لا ترفع `.next` أو ملفات البيئة أو الأسرار. قبل الدمج، راجع `git diff --staged` وتأكد من أن التعديلات تخص النطاق المطلوب فقط.

## Git وVercel

الفرع الإنتاجي هو `main`. أي دفع ناجح إلى `origin/main` يفترض أن يطلق نشر Vercel تلقائيًا إذا كان مشروع Vercel مضبوطًا على `main` كـ Production Branch. بعد الدفع، راجع سجل Deployments في Vercel واختبر الصفحة الرئيسية و`/sectors` و`/specialties` و`/contact`، إضافة إلى الروابط ذات معاملات `audience` و`specialty`.

آخر دمج منشور في GitHub قبل وثيقة التسليم هو commit الدمج `ab0a16f`. هذه الوثيقة والتعليقات داخل الملفات تشرح المنطق، ولا تستبدل الاختبار قبل النشر.

## ما لم يُنفذ بعد

لم تُنشأ صفحات مستقلة للخدمات مثل العقارات أو عقود الشركات أو المنازعات المدنية. هذه هي الخطوة التالية المقترحة بعد قياس الفهرسة والزيارات من Search Console، وليست جزءًا من هذه الجولة.

لم تُضف تقييمات أو شهادات عملاء؛ لا تُضاف أي شهادة إلا بعد الحصول على موافقة صريحة وصياغة صحيحة لا تكشف بيانات سرية.

لم يتم تعديل قواعد Supabase أو تطبيقات Qayd وQayd Office في هذه الجولة؛ النطاق كان موقع `ostazlaw` فقط.

## ملاحظة عن الملف المحلي

قد يظهر مجلد `docs/superpowers/plans` محليًا من جلسة التخطيط السابقة. لا تضفه إلى commit إلا إذا أراد الفريق الاحتفاظ بخطة التنفيذ في المستودع؛ ملف `DEVELOPER_HANDOFF.md` هو وثيقة التسليم المقصودة.

## حالة النشر

تم اختبار البناء محليًا في جولة التعديلات السابقة. بعد أي تغيير جديد، يجب إعادة `npm run build` قبل الدمج، ثم التأكد من أن `origin/main` يحتوي على commit المتوقع وأن Vercel بدأ Deployment جديدًا.

### خلاصة سريعة للمطور

1. اقرأ التعليقات أعلى أقسام SEO ومسارات التحويل قبل تعديل النص.
2. حافظ على تمرير `audience` و`specialty` إلى نموذج التواصل.
3. لا تحذف سمات الوصول من بطاقات التخصصات.
4. اختبر البناء والروابط قبل الدفع إلى `main`.
5. راجع نشر Vercel بعد كل دفع إلى `main`.
6. أبقِ الموقع مركزًا تسويقيًا على العقارات والعقود والمنازعات المدنية وخدمات الأعمال، دون ادعاءات أو ضمانات.
